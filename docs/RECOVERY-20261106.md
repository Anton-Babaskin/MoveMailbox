  monitoring timers paused and both application writers stopped gracefully.

## New VPS sequence

1. Provision a clean supported OS (the previous VM used Ubuntu 24.04) and
   owner-controlled SSH. Preserve recovery materials independently; do not
   upload the decryption identity to the old host or publish private settings.
2. Restore/build from reviewed source or the saved exact images. Follow the
   [paired backup runbook](BACKUP-RUNBOOK.md): validate the entire pair before
   installing it into fresh volumes. Never overwrite the sole surviving copy.
3. Recreate the dedicated deployment with new IP/NIC/DNS choices. The old
   network/firewall/SSH files are references, **not a root filesystem overlay**.
   Adapt the NAT-public-IP egress deny rule and avoid conflicts with VPS networking.
   With no active envelopes, rotate service keys/tokens for the fresh closed pilot
   as an explicit coordinated deployment step; do not blindly mix old/new keys.
4. Point the approved app hostname to the new VPS, issue/serve a matching trusted
   certificate and verify exact Host/Origin, guest ownership, SSE/cancel and one
   disposable real-mail migration. Ordinary VPS 443 needs no old Proxmox DNAT.
   Do not reuse the expired October manual DNS challenge.
5. SMTP code/timer were preserved, but `notify.json` was absent: actual delivery
   was not configured. Obtain credentials via hidden input; verify receipt.
   Certificate automation and public-access approval remain launch gates.
6. When retiring the old public IP, remove/repoint old staging DNS so it cannot
   keep pointing to an address later assigned to somebody else. GitHub Pages
   and apex/www DNS must be preserved independently.
